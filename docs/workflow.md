# 完整工作流：从一份课件 PDF 到内容完整的讲解

> 给想理解这套流程的人看——无论接下来动手的是你还是 AI agent。
> 可照抄的完整命令与 Agent 执行规范在 `SKILL.md`；写讲解的质量标准在 `references/content-quality.md`；
> 36 条真实踩坑记录在 `references/pitfalls.md`。

## 一屏看懂

```
课件 PDF
   │
   ▼
① 环境自查 + 机械部分        run_all.py 一条命令：建骨架 → 渲染逐页图 → 组装 → 报进度
   │                          （产出 _extract/page-NN.png —— 后面一切的原料）
   ▼
② 逐页看图写讲解             唯一需要「智能」的一步：看每一页的渲染图，写出左侧讲解
   │                          （agent 代做 = 你什么都不用写；手工 = 你自己写）
   ▼
③ 复检 + 三重校验 + 截图     run_all.py --skip-init --skip-prepare / check_math / check_ui / probe / shot
   │
   ▼
单文件 HTML 交付              断网可开、公式正常、标记可恢复，附带「原稿问题清单」
```

关键认知：**第 ② 步是这套流程的价值所在，也是它和「PDF 转文字工具」的根本区别。**

## 第 ① 步：机械部分全自动

```bash
pip install -r requirements.txt
python scripts/kitpath.py                              # 自查：python / node / 浏览器 / 依赖
python scripts/run_all.py "<课件>.pdf" --out <输出目录>  # 一条命令跑完机械部分
```

跑完你会得到：

| 产物 | 是什么 | 为什么重要 |
|---|---|---|
| `_extract/page-NN.png` | 每页一张的高清渲染图 | **逐页看图看的就是它**。PPT 导出的 PDF 文字层不可靠——数学符号的字体映射常常是坏的（`¡` 可能实际是减号、`¼` 可能实际是 π），只读文字层必然讲错公式。这是踩过真坑的结论，详见 `references/pitfalls.md` 第一节 |
| `content/` | 逐页讲解骨架 | 待填的「题卡」：区块结构、页码锚点已就位，只等讲解内容 |
| `_katex/` | 离线 KaTeX | 字体已内嵌，产物公式渲染完全不联网 |
| 单文件 HTML | 半成品 | 结尾会报 **`内容进度：待补页面 N / M`**——这个数字是第 ② 步的工作量 |

## 第 ② 步：逐页看图写讲解（核心）

这是唯一需要智能的一步，两种执行方式：

**AI agent 代做（推荐）**：把课件和这个仓库交给 agent（见 README「让 AI 替你做」）。
Agent 会逐页用「眼睛」看渲染图——逐页读图是写进 `SKILL.md` 的硬性纪律，不许跳过——
然后按规范写讲解、自己复检到「待补 = 0」、跑完校验才交付。你只需要审。

**自己写**：用编辑器看 `page-NN.png`，往 `content/*.html` 里填讲解。
骨架、公式写法、提示框配色这些硬规范全部集中在 `SKILL.md` 的「分步流程」一节
（那里同时也是给 agent 的指令，人类照着执行完全兼容）；
写多好算合格，看 `references/content-quality.md`——简单说：**每页先说这页在干什么、结论前置、
补上原文跳过的推导、原稿有错如实标注、跨页伏笔要回收**。

无论谁写，产物里都要求显式区分「原文有什么」与「讲解者加了什么」
（绿=直觉、蓝=补充推导、红=原稿问题、灰=原文引用）——读者一眼就能校准信任。

## 第 ③ 步：验证后才算交付

改完讲解，重跑一次流水线（跳过已完成的建骨架与渲染，快得多）：

```bash
python scripts/run_all.py "<课件>.pdf" --out <同一目录> --skip-init --skip-prepare
```

它会自动跑完三重校验与截图。各管一段、缺一不可：

| 校验 | 抓什么问题 |
|---|---|
| `check_math.js` | 公式能不能渲染、中文有没有混进公式、标签配对、缺字 |
| `check_ui.py` | 四类交互的「接线」是否完好 |
| `probe.py` + 探针 | **结构有没有被改坏**（截图看不出 `<mark>` 里混进了块级元素这种事） |
| `shot.py` | 长相与真实交互状态 |

## 为什么是这个目录结构

- **`assets/` 四个文件是耦合的**：`shell.html`（骨架）+ 两个 CSS + `site.js`（交互）。
  改一个不同步其余，页面要么样式裸奔要么交互失效——`check_ui.py` 就是为拦这个而存在。
- **`build.py` 用非贪婪正则拼装区块**：所以模板注释里绝不许出现 `<section>` 这类字面标签，
  否则拼装提前收尾，症状是「图在文件里、DOM 里查不到」，极难排查。
- **`vendor/katex/` 随仓库分发**：一次制作离线 KaTeX（字体转 data URI），
  之后所有项目零网络依赖，也不依赖 CDN 的可用性。
- **所有脚本用相对自身位置定位资源**：整个目录拷到任何机器、任何用户名下都能跑，
  「外部程序在哪」统一问 `scripts/kitpath.py`（环境变量 → PATH → 常见安装位置）。

## 常见问题

- **断网能用吗？** 能。公式字体内嵌在产物里，整个流程除 pip 安装外零联网。
- **产物多大？** 不内嵌原 PDF 约 1–5 MB（几十页）；内嵌原 PDF ≈ 原 PDF × 1.34 + 缩略图。
- **换设备后「打开原文件该页」失效？** 默认深链是绝对路径，换设备必失效。
  两条路：原 PDF 与产物放同目录改相对路径，或 config 里开 `embed_pdf` 把原文件 base64 内嵌。
- **PPTX / Keynote 输入？** 只支持 PDF。PPTX/Keynote 请先自行导出 PDF——
  刻意不引入 LibreOffice 依赖，导出时的字体与版式由你决定，更可控。
